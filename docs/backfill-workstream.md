# Backfilling connection options — workstream handbook

Everything needed to pick this up cold. Written 2026-09-22 at the end of a long session.

Companion doc: `connection-options.md` holds the domain model (filename grammar, node
groups, sockets, bands). This one holds the *process*, the tools, and the traps.

---

## 1. What this workstream is

The released tree `~/Dropbox/.../OpenForge/tiles` is missing connection-option variants
for many pieces — `openlock+unsupported` above all, plus side-lock variants. The job is to
find every gap, build what can be built, and record why the rest can't.

**dungeon_stone / separate_wall / primary_walls is the reference implementation.** Get it
complete, then replicate the same pattern to the other sets.

Hard rules Devon set:

- **Never write into the production tree.** Generated files go to
  `OpenForgeDevelopment/tiles/<texture>/updates/<mirrored release path>/`. Moving them to
  `OpenForge/` is a separate release step.
- **Cores live in** `OpenForgeDevelopment/tiles/<texture>/peripherals/<family>/`, flat.
  (`basics/Walls/` holds the hand-made wall cores that predate this work.)
- **One family at a time**, so Devon can track it. No bulk runs across families.
- **Devon reviews every batch** before it counts as done.
- Columns and bases are **out of scope** for now.

## 2. The queue: `docs/option-gaps.tsv`

One row per missing file. Regenerated by `bin/option-gaps.py`; **the `status` column is
preserved across regenerations** and is the only human-supplied column.

| column | meaning |
|---|---|
| `texture` | `dungeon_stone`, `cut-stone`, … |
| `family` | path under `tiles/`, e.g. `dungeon_stone/separate_wall/primary_walls/drain` |
| `variant` | `<texture>#<piece>.<size-or-letter>`, e.g. `dungeon_stone#drain.A` |
| `missing_option` | canonical connection string, e.g. `openlock+unsupported,side` |
| `gap_class` | `family` / `family_type` / `canonical` — how the gap was inferred |
| `likely_deliberate` | option present for exactly one variant, or missing from exactly one |
| `has_core` / `core_path` | whether a core was found, and which |
| `node_group` / `set_args` | what to apply; `;` separates chained groups and settings |
| `out_path` | where the file goes |
| `status` | **the working column** — see below |

### Status conventions

```
(empty)              outstanding
built …              built, awaiting Devon's review
REVIEWED … ok | …    Devon approved
REJECTED …           Devon rejected; reason follows
accepted: …          impossible, with the evidence inline (probe %, missing geometry)
blocked: …           can't build for a named reason
```

Always put the *evidence* in the status, not just a verdict — `accepted: side ports
blocked by the archway (probe low/mid 27.1/19.0%, needs 100%)` is worth far more later
than `accepted`.

### How gaps are inferred

Three tiers, strongest first:

1. **`family`** — a sibling variant in the same family has the option.
2. **`family_type`** — absent from this family, but present in the same family type
   (family path minus the texture) in other textures. Catches a texture that never got an
   option at all.
3. **`canonical`** — **unsupported crosses every openlock option the family has.**
   `openlock` ⇒ `openlock+unsupported`, `openlock,side` ⇒ `openlock+unsupported,side`,
   `openlock,pegs` ⇒ `openlock+unsupported,pegs`. These combinations exist nowhere in the
   tree, so no empirical tier can propose them.

## 3. Tools (`bin/`)

**Not all of these run in the bpy container.** `option-gaps.py`, `apply-gaps.py`,
`build-cores.py`, `reset-for-core.py` and `seed-gaps.py` are plain stdlib Python that run
on the host and shell *out* to `bin/ab`; `make-core.py`, `make-ports.py`,
`make-pegs-group.py` and `assemble-tile.py` need bpy and run inside it; `qc-updates.py`,
`stepwise-core.py` and `audit-cores.py` need trimesh but not bpy. `bin/ab` is the docker shim; **`AB_ENTRYPOINT=python bin/ab
<script.py>`** runs a bpy script with the right mounts (`/home`, `/mnt`, `$PWD` → `/work`).

| tool | what it does |
|---|---|
| `option-gaps.py` | Survey the release tree → the queue. Preserves `status`. Canonicalizes connection strings. Skips `blueprint/` (temple prep). |
| `build-cores.py <texture> <family-path>` | Assemble every missing core for a family from shipped openforge tiles. Refreshes the queue afterwards. |
| `make-core.py` | One core: openforge tile + lockless base → join → remesh → decimate → **manifold repair**. `--flip` turns the tile end-for-end for a `+reverse` variant; `--demo` self-checks the flip maths. |
| `make-ports.py` | Probe ports (**fill** + **overhang**) and cut the green ones. `--probe-only` to just report. |
| `apply-gaps.py <texture> [--option SUBSTR] [--dry]` | Build queue rows. Skips rows with a status or an existing output, so it's resumable. |
| `reset-for-core.py --texture T '<core substr>' …` | After a core is re-sculpted: delete and un-status the **side-lock** rows built from it. |
| `audit-cores.py [--mark]` | Is each `*.core.stl` a real core? A genuine core is ~6mm taller than its shipped openforge sibling. |
| `seed-gaps.py <texture> <folder> [--dry]` | Queue rows for a texture with nothing released (§6b). Skips rows already present. |
| `stepwise-core.py <in.shells.stl> <out.core.stl>` | Union shells one at a time; hold and report any that leave it non-manifold, float, sit inside, or make voids (§6b). |
| `qc-updates.py <updates-dir-or-file> [--fix]` | Per-file watertight / bodies / nm / z / volume vs `openlock` sibling. `--fix` drops zero-volume fins. |
| `make-pegs-group.py` | Adds the `Pegs` node group to a library (already done for A/IA/Q). |

### The per-family loop

```
1. build-cores.py <texture> <family-path>        assemble cores from shipped tiles
2.   → Devon checks them (3D Builder); some need repair
3. make-ports.py --probe-only  per core          fill % and overhang (signed mm) per port
4.   → Devon sculpts any core reporting overhang
5. reset-for-core.py …                           if any core changed
6. apply-gaps.py <texture>                       build
7. QC: height / watertight / volume vs shipped siblings, PER FILE.
   **Compare OURS-WITH-SUPPORTS against the shipped `openlock`; that should be within
   a few tenths of a percent.**  Do not use a fixed expectation for the unsupported
   file: support volume scales with wall length, so the delta is letter-dependent --
   21.8mm3 on IA (1x, 0.21%), 43.6mm3 on BA (1.5x, 0.26%), 153.5mm3 on Q (4x, 0.54%).
   A small piece can even come out *larger* than shipped (`door+rectangular narrow.IA`
   reads +0.07%: our core is +0.29% and the supports are only -0.21%).
   Building the supported version from the same core is the diagnostic -- it separates a
   core that differs from the shipped geometry from a node group doing the wrong thing.
   boss_door was -4.73% on that test where door+arched was -0.10%.
8.   → Devon reviews; mark REVIEWED or REJECTED
```

## 4. Domain facts you must not re-derive

### Cores

A **core** = the wall with a base on it and **no locks**. It's what every node group
expects. The openforge variant is the same wall with the bottom 6mm cut off, so:

```
core = openforge tile (lifted onto its base) + Base-<L>.<Texture>
       → join → remesh (voxel 0.1) → decimate 0.1 → union repair
```

- **The tile is usually dropped to z=0** because Devon repairs Blender exports in 3D
  Builder, which recentres. Lift it back by the base's own height — measure, don't assume 6.
- **Placing the tile on the base is two steps, and it used to be one.** A real grid
  offset is a whole multiple of 15mm (the wall grid) and is rounded to it. *Then* the tile
  is **squared** on the base: measure the wall band just above the base against the base
  itself, and apply the residual in X and Y, capped at half a grid step.

  The one-step version left three holes, all silent, all found on 2026-09-22:

  | case | old behaviour |
  |---|---|
  | offset < `NOISE` (1mm) | dismissed as mesh noise — boss_door out 0.84mm, all 8 cores rejected by eye |
  | `NOISE` <= offset < 7.5mm | judged real, then `round(x/15) == 0` corrects it by **nothing**. Real hole in the code; no confirmed instance yet |
  | any X offset | never corrected at all |

  Measure the wall **band**, not the tile's whole bounding box: anything protruding in Y
  higher up (a boss door's skull) drags a full-bbox centre off, and the band ignores it.
  After squaring, all 14 `door+arched` cores land within 0.006mm.

**The base is the reference, and it must be the base object's full bounding box.**
`make-core.py` prints `base-vs-wall dx/dy` and flags >0.1mm; `build-cores.py` surfaces the
flagged ones. An earlier version of that check took a z-band of the *finished core* as the
base reference and produced a convincing false alarm: **`Base-D` is not a box.** Between
z=1 and z=5 it is undercut to `y=[-0.250, 6.522]` while its footprint is
`y=[-6.350, 6.522]`, putting the "centre" at +3.136 and reporting a tile that was square
to 0.047mm as 1.85–2.25mm out. Never assume a base is a prism.
- **Base object names aren't consistent**: `Base-A.Dungeon Stone` but
  `Base-D-Dungeon Stone`. Match `^Base-[A-Za-z]+[.-]<Texture>$`.
- **remesh+decimate is never manifold.** `make-core.py` runs `union.py`'s repair, which
  matched a hand 3D-Builder pass to 3 parts per million on volume. Roughly 1 in 10 cores
  still needs Devon's eye — **nothing measurable in trimesh distinguishes those**
  (watertight, single body, sane euler all pass on a core 3D Builder rejects).

### `+reverse` is a flip, not a separate part

The tile is **asymmetric along its length**, so a `+reverse` variant is that same part
offered the other way round — the tile turned end-for-end before the base goes on. It is a
180° rotation about Z, not a mirror: handedness survives, so the part stays printable.

`+reverse` therefore ships **no openforge tile of its own** — it appears only under
`openlock/`, where the locks are already cut, so that file is not a core source. It does
not need one. `build-cores.py` spots `+reverse` in the variant name, takes the plain
sibling's tile, and passes `make-core.py --flip`, which pivots on the **base's** XY centre
(X is never corrected downstream — only Y and Z are — so pivoting on the base is what
keeps the flipped tile square on it).

Do **not** try to verify a built reverse core by comparing it to the shipped reverse
piece's volume. `%block` matches its plain sibling to 0.05%, but `%eroded` differs by
~4.8%, because erosion is generated per piece — the shipped reverse-eroded tile carries a
different erosion instance, and so will ours. That is expected, not a defect.

### Side ports

Three bands, **19mm apart**, both ends of the wall, ports 11.4mm wide regardless of wall
width:

```
Side.Low    z=[ 7.90, 23.90]
Side.Mid    z=[26.90, 42.90]      (was called the "upper" band before High existed)
Side.High   z=[45.90, 61.90]      building_facades only — those tiles are ½" taller
```

High reads ~27% fill on a standard wall and is correctly skipped. **One library serves
both heights; the probe decides per piece.** No flag.

**Two independent checks, both required for a port to be cut:**

- **fill** — material *inside* the port block. **100% is the rule, but the number is a
  proxy.** What actually matters is whether material is missing *where the clip sits*, not
  anywhere in the block. A drain cavity or arrow slit in the band shows up as 65%, 27%,
  19% and is genuinely impossible; but `door+arched+narrow.A` read **99.7 / 99.8%** and
  Devon took it — the archway clips a corner of the block that the clip never touches.
  So: below ~99%, accept the port as impossible. At 99%+, ask, because only the model
  tells you whether the missing sliver is in the clip's way.

  **And the answer can differ per lock style.** On `narrow.A`'s Mid ports the OpenLock
  clip clears the missing sliver but the DragonLock clip does not, so that shape gets
  openlock side locks only. A 99.7% fill is therefore not a single yes/no — it is a yes
  for one style and a no for another. (Release already ships
  `narrow.A.openforge,side+dragonlock.stl`; that predates this workstream and is not a
  queue row, but it is presumably carrying the conflict.)
- **overhang** — material *outside* the mating plane, within the port's band. Must be
  **0**, and Devon's reason is not clearance: material past the plane changes the mesh
  exactly where the port block gets unioned on, which makes *that boolean* less reliable.
  Fill can read a perfect 100% while this is bad. Fixed by Devon sculpting the core.

  **Measure the protrusion in mm, not the volume.** Volume tracks the area of the smear
  rather than its depth, and ranks ports wrong — on a boss_door core one port read
  0.02mm³ while standing 0.054mm proud, and another read 0.03mm³ at only 0.042mm proud.
  A 0.33mm³ reading looked borderline as a number and was obviously wrong on screen.
  `make-ports.py` gates on `PROUD_MAX = -0.01mm` — **negative on purpose**: the texture
  must sit *behind* the plane, not merely flush. The probe box reaches `BEHIND = 2.0mm`
  inside the plane as well as `OUTSET` past it, because a box starting at the plane comes
  back empty when nothing protrudes and so cannot tell "flush" from "recessed 0.5mm".
  (`BEHIND`, **not** `INSET` — that name is already taken by the fill probe at `25.4/8`,
  and reusing it silently changes every fill reading.) The probe also prints the y/z of
  the worst point so the spot can be found in Blender directly.

#### Measured, not assumed: what protrusion actually does

`make-ports.py --face-check` unions each port block on its own and reports what the
boolean did to the block's mating face. On boss_door cores, 2026-09-22:

```
proud        face verts       non-manifold edges
-0.039       4 ->   4  (+0)   0 -> 0
-0.004       4 ->   4  (+0)   0 -> 0
+0.002       4 ->  12  (+8)   0 -> 0
+0.004       4 ->   9  (+5)   0 -> 0
+0.046       4 ->  61 (+57)   0 -> 0
```

**It flips exactly at zero.** Two microns proud fragments the face into 8 extra vertices;
four microns of clearance is clean. Non-manifold edges never appeared, so the cost of a
flush core is a fragmented mating face, not an invalid mesh. The empirical requirement is
`proud < 0`; `-0.01` is **margin, not requirement**, because the measurement's own noise
is ~0.004mm.

A red port gets **neither block nor cut** — an unused block leaves a pointless flat pad.

#### The sculpt gets it to zero; `--trim` gets it past zero

A hand sculpt reliably converges on **flush**, not behind — boss_door landed at 0.000
±0.005 and door+arched did the same, going from +0.12…+0.26 down to ±0.006. That is the
natural stopping point: you stop when the protruding material is gone, which is zero. And
zero is the one value that is neither pass nor fail, inside the probe's own ~0.004mm noise.

So the pass is **sculpt, then trim**, and the order matters in both directions:

- **The sculpt cannot be skipped.** A cut at the mating plane cannot see texture *flowing
  into the port from above its face* — Devon's words — and that is exactly what a sculpt
  fixes. `--trim` only guarantees the last few hundredths.
- **The trim cannot be skipped either**, unless you are happy with ports landing on the
  boundary at ±0.005.

`make-ports.py --trim` cuts each usable port's band back to `CLEARANCE = 0.05mm` behind
the plane and rewrites the core. On door+arched all 24 ports came out at exactly -0.050
with 0 non-manifold edges. `--min-fill` decides which ports get trimmed (default 99.95;
door+arched `narrow.A` used 99 for its 99.7% Mid ports). A port that will never be cut is
skipped, so it gets no pointless pocket.

**The cut box is the port footprint plus a 0.3mm margin.** Matching the footprint exactly
leaves material surviving on the boundary, and the probe measures that same footprint, so
it finds it: ports came back at -0.021 and -0.025 instead of -0.050, every worst point on
a band edge. The margin puts the measured band strictly inside the cut.

**Back up hand-sculpted cores before trimming.** A sculpt is not regenerable; the trim is.

### Library layout (all five now aligned)

```
Port Block-<L>.Side.{High,Mid,Low}[.A/.B]
Port Block-<L>.Side.Minimal[.{High,Mid,Low}]     barely larger than the port; used when
Port Block-<L>.Side.Dragonbite[.Low]             you don't want to muss the texture
Negative-<L>-Side.{Openlock,Dragonbite,Infinitylock}.{Band}[.A/.B]
```

- **Never resolve a cutter by name.** Spellings differed wildly before the rename pass and
  will drift again. `make-ports.py` matches cutters to port blocks **by position** and
  reads the style off the name.
- **Ports are discovered**, not hardcoded: anything matching
  `Port Block-<L>.side[.<band>].<A|B>`.
- **Filament** = corner pieces only, and corners never go in building_facades, so it never
  needs a High band. **Infinitylock** is dormant — renamed for consistency, not extended.
- **Pegs** exist only for **A, IA, Q** (`Pegs-<L>-Wall` objects). Peg rows for BA and D are
  impossible and marked accepted.

## 5. Traps that have actually bitten

**Blender / bpy**

- **Geometry node groups evaluate in the object's LOCAL space.** Moving `obj.location`
  before applying one does nothing at all. Transform the **mesh data**. (Object transforms
  *do* matter for `join()` and object-operand boolean modifiers — different rule.)
- **`bmesh.calc_volume()` reads mesh data and ignores object scale.** A scaled box measures
  as a unit cube — every port read a confident 100%.
- **`import bmesh` must come after `import bpy`.** Alphabetical import order raises
  `ModuleNotFoundError`.
- **A node group with no user is dropped on save.** Set `use_fake_user` *and* `asset_mark()`.
- **`Object Info` defaults to `ORIGINAL` transform space**, which returns geometry in local
  coords — present but unpositioned. Use `RELATIVE`.
- **`GeometryNodeMeshBoolean` with `operation='UNION'` has no `Mesh 1` socket** — it
  collapses to one multi-input.
- **Solver**: libraries now default to **MANIFOLD** (243 nodes switched 2026-09-22). EXACT
  collapsed `wall.D` to a 162-poly sliver and left `OpenForge+Side` output non-watertight.
  `ab gn apply --solver` still overrides either way.
- **`Top-<L>-Plain` must start at exactly z=6.00.** `OpenForge` cuts with `Filter.Base`,
  whose top face is ~229k triangles; the top-buffer plate's bottom face, coplanar with the
  cut, is what replaces that dense cap with 2 triangles. In `library.primary.A.blend` the
  plate sat at 6.01, so every A openforge output shipped a 113k-sliver bottom face that 3D
  Builder could not repair (found 2026-09-23 on nova_trail). QC signature: tens of
  thousands of flat faces at z=6.00. Devon's fix was a new `Filter.Base` in the A library
  with 384 faces (the dense one was subdivided on purpose, as more likely to boolean
  cleanly): A openforge bottoms dropped to ~160 triangles and files to ~1/4 the size.
  The other four libraries still carry the 229k-face cutter, masked by their plate.
- **The openforge cut plane grazes stone texture** and leaves paper-thin flanges. Use
  `ab gn apply --nudge-z -0.02` so it bites into solid material. The piece comes out 0.02
  shorter at the top; the base face stays at 6.000.

**Process**

- **Cores don't enter the queue until `option-gaps.py` re-runs.** `apply-gaps` then
  silently builds nothing. `build-cores.py` now refreshes automatically — nothing else does.
- **Name matching leaks across textures.** `cut-stone#portcullis.A` ends with
  `portcullis.A`; `rough_stone#wall.2x.A` contains `#wall.2x.A`. **Always scope by
  texture.** This has now bitten four times, and the fourth was not a core name but the
  `family` column: `family.endswith("/primary_walls/boss_door")` matches *every* texture,
  so a status update meant for 11 dungeon_stone rows silently marked 16 cut-stone rows
  REVIEWED as well. The family path is `<texture>/<sub...>`, so it is only unique *with*
  the texture — filtering on a family suffix is the same bug in a new column. Caught by
  the row count not matching (27 marked where 11 were expected); nothing else would have
  shown it.
- **Libraries change under you.** Dropbox sync lag means a read can predate Devon's save.
  Check the `.blend` mtime after he says he's saved.
- **Verify the artifact, not the exit code.** Three times a command exited 0 and printed
  something plausible while doing nothing — an unknown argparse flag filtered out by a
  narrow grep, a stale Docker image, a no-op nudge. Grep the installed module; check file
  timestamps; count files.
- **Don't narrow greps on command output.** Every one of the above hid inside a
  `grep -E "^#|error"`.

**Data**

- **Not every `*.core.stl` is a core.** `dungeon_stone/basics/Walls/Parts/*` are finished
  *openforge* bodies under a core name — Devon resizes and curve-modifies them to build
  curved walls. Building from them silently yields walls missing their bottom 6mm.
  `audit-cores.py` catches this.
- **`blueprint/` is temple prep** — same-named copies, sometimes already cut. Excluded.
- **The same piece under two spellings creates phantom gaps.** The survey keys on the
  variant name, so an inconsistently-named twin looks like a piece that is missing every
  option it does not have under that spelling. Found twice, fixed both times by renaming
  the shipped files (a release-tree change — Devon's call each time):

  | case | phantom rows |
  |---|---|
  | `wall,drain` vs `drain` | 20 |
  | `door+rectangular.D` / `.Q` vs `+wide.D` / `+wide.Q`, eroded openforge only (2026-09-22) | 14 of 58 |

  **cut-stone still has the `wall,drain` alias** (8 files).

  How to spot it: a variant whose options are a strange subset — `door+rectangular.D`
  had *only* `openforge`, while `+wide.D` had everything else — and whose twin uses a
  different name. Confirm on geometry before renaming: the eroded `.D` openforge tile and
  the block `+wide.D` openforge tile had identical extents `[76.2, 13.03, 44.8]` and
  differed only by erosion (-3.5% volume). Remember the `-thumb.png` alongside each STL.
- **`%block` and `%eroded` twins are NOT identical geometry** — erosion changes topology, so
  an Euler mismatch between them is normal. (I proposed it as a defect detector; it isn't.)

## 6a. boss_door: closed 2026-09-22 (16 built, 12 accepted)

The 12 accepted are the `+reverse` openforge rows: **an openforge piece has no base, so
it is simply turned around when placed.** `+reverse` exists only because openlock bakes
the base in. This is a *straight-wall* rule — curved walls are chiral and the release tree
does ship `+reverse` openforge files for `curved_walls/magnetic` and for curved stairs, so
it is deliberately NOT encoded in `option-gaps.py`.

### Generated cores were rejected

`build-cores.py` produced all four non-reverse cores clean on every number we have —
+6.00mm over their shipped tile, watertight, one body, `shells=1 solids=1 voids=0` — and
the two reverse cores it got through before being stopped were correct *as flips*: volume
matched the plain sibling to 0.003% and Y mirrored exactly. **Devon rejected them all by
sight anyway**, non-reverse included, and is building these cores by hand.

This is the "1 in 10 needs Devon's eye" case from §4, and it is worth stressing that
**nothing measurable in trimesh caught it** — again.

One lead, recorded as a lead and not a conclusion. Measuring the base band (z 1–5) against
the wall band (z 8–12) in each core, the base sits **~0.84mm off in Y** relative to the
wall, with the sign flipping between plain and reverse:

```
+dungeon_door                base is +0.036 in x, +0.834 in y vs the wall
+dungeon_door+reverse        base is -0.038 in x, -0.838 in y vs the wall
+dungeon_door+skull          base is +0.037 in x, +0.837 in y vs the wall
+dungeon_door+skull+reverse  base is -0.035 in x, -0.838 in y vs the wall
```

`make-core.py` used `NOISE = 1.0` as a Y floor, so a 0.84mm offset was read as mesh
noise and never corrected.

**Confirmed by Devon's hand-built replacements.** The same measurement on those reads
`dy = +0.004 … +0.032`. The texture is identical in both sets, so if 0.84mm had been
texture asymmetry it would have persisted; it did not. **The 0.84mm was a real
misalignment, and `NOISE = 1.0` hid it.**

The fix is `make-core.py`'s second step: it squares the tile on the wall band just above
the base (not the bounding box, which a boss door's skull drags off-centre), and `NOISE`
now only decides whether the tile needs lifting in Z.

**Stale cores:** six generated cores are sitting in
`peripherals/boss_door/` (4 non-reverse, 2 reverse). Until they are replaced,
`apply-gaps.py` will happily build from them, because the queue only knows `has_core=yes`.

### boss_door outputs are ~4.7% light — unexplained

Measured 2026-09-22, after door+arched gave a baseline to compare against:

```
                     ours, supports ON, vs shipped openlock
door+arched wide.Q            -0.10%      core from build-cores.py
boss_door   dungeon_door.Q    -4.73%      core hand-made by Devon
```

Same node group, same flag, same letter — so the difference is in the core, not the
build. boss_door's hand-made core yields a piece 2451mm3 lighter than the shipped
openlock on a ~52000mm3 part. The files are watertight, single-bodied and Devon passed
them by sight, so this is not a known defect; it is a number that does not match the
baseline, found only after the baseline existed. Worth resolving before those files go to
release.

An earlier note claimed the shipped `%eroded+reverse` boss_door files looked like they
already lacked supports. **That was wrong** — the 2887mm3 gap between the `%block` and
`%eroded` reverse twins is 19x the support volume and is erosion depth, not supports.

## 6b. nova_trail walls: first unreleased texture (started 2026-09-22)

**Released 2026-09-30.** All 235 wall rows were REVIEWED/accepted, and floors, s2w floors and
columns were confirmed. openforge-renamer moved everything from `nova_trail/updates/` into
`OpenForge/tiles/nova_trail/` (same relative paths; names checked against its conventions,
`side,pegs` ruling included). The seeded queue rows keep their now-stale `updates/`
`out_path` as history.
Same day, Devon had the 12 decoration walls (bypass, conference_room, console, dedication,
engineering, environmental_controls, fancy, monitor, pipe_access, pipe_access2, replicator,
tube) moved into one release folder, `separate_wall/primary_walls/wall+decorations/`
(filenames unchanged). `wall`, `wall+door`, `wall+window`, `wall+swappable` stay separate.
**Pulled from the Sept release (2026-09-30):** `wall+decorations`, `wall+swappable` and
`wall+window` moved back to `nova_trail/updates/separate_wall/primary_walls/` to ship next
month. The release tree keeps only `column`, `wall`, `wall+door`.

nova_trail has **no separate walls in the release tree**, so `option-gaps.py` proposes
nothing for it. `bin/seed-gaps.py <texture> <dev-folder>` writes rows for every
`<tex>#<piece>.<size>.<L>.core.stl` in the folder, using dungeon_stone `wall`'s option
set and folder layout (13 options; **pegs only on the plain `wall` piece**, and only for
A/IA/Q -- feature walls never get pegs, Devon 2026-09-23). Rows are `gap_class=seeded`,
and `option-gaps.py` carries them over verbatim on regeneration.

Sources are `basics/walls/nova_trail#<piece>.<size>.<L>.{shells,core}.stl`; the AENOVA
originals in `orig/` were renamed to feature names by Devon, so no gaps there.

**Cores are hard-surface CSG** (made by `ab core`), not sculpts. Two recurring defects:

- **Zero-volume fins.** manifold3d's output is clean, but writing it as float32 STL folds
  a few near-coincident triangles into fins hanging off shared edges. They break
  watertightness and survive the node group into the output. Dropping components under
  1mm3 fixes most; `bin/qc-updates.py --fix` does it to outputs. Originals kept as
  `*.core.pre-clean.stl`.
- **One reused sub-assembly at z~41-46**, set 2.3-4.0mm into the face, leaves slivers
  that fin-dropping cannot fix (`wall+tube`; `wall.2x.A` was hand-fixed by Devon 2026-09-23 and built clean) and is a **separate floating
  body** in `wall.3x.D` / `wall.4x.Q` (26-30mm3). Blocked pending a fix in `walls.blend`.

**Diagnosing a dirty core: union the shells one at a time.** Largest first, round-trip
each intermediate through float32 STL, and hold any shell that leaves the result
non-manifold. On `4x.Q` (2026-09-23) this showed the z~41-46 detail placed three times:
one copy overlapped the wall (clean), one touched it face-to-face with zero overlap
(non-manifold), one sat 0.0012mm off it (floating) -- measured with manifold3d's
`min_gap`. Devon re-exported the shells with all three overlapping and the core came
out as one body. Devon then re-exported `2x.A`, `3x.D`, `1x.IA`, `1.5x.BA`, the corner and
`wall+tube` the same way; all came out one body. On `wall+tube` the culprit was not a
detail but two *wall sections* butted face-to-face at x=+/-15.22 with zero overlap.
**Rule: shells that should join must overlap, never just touch.**

**Side ports: all RED on all 15 cores probed.** Low 93-99.7%, Mid 78-99.2%, High ~30%,
and the end faces sit exactly flush (+/-0.01). The fill is nearly identical across every
feature, so it is the nova wall's *end profile* being narrower than the port block, not
a feature void. **Devon's call (2026-09-22): the walls are thin — build anything close,
and he deletes the ones that don't work.** So the 100% rule does not apply to nova_trail:
everything >=90% was built through the node group as usual (no trim; the flush end faces
are CSG, not texture). Only `wall+swappable` (Mid 78%) was accepted as impossible.

### Floors (confirmed by Devon 2026-09-29; not in the queue)

`basics/floors/nova_trail#floor.<size>.<L>.core.stl` -> `updates/floors/floor/{openforge,
openlock,openlock+unsupported}/nova_trail#floor.<size>.<opt>.stl` (size in the name, not
the letter, as dungeon_stone ships). openforge = core trimmed at z=6, left at z=6.
openlock / unsupported = core minus `Negative-<L>.Triplex` / `...+Supportless` from
`generic/openlock_base/base_negatives.blend`, done in manifold3d (some cutters are
multi-shell; union them first). Unsupported reads -0.8 to -2.7% vs openlock on floors.

- **Strips are not shipped**, except the 2x strip, which is the **AS floor**

### Columns (2026-09-29)

`library.columns.blend`: `Column-L` (OpenLock + DragonBite, with port blocks) and
`Column-Corner` (OpenLock, DragonBite, Filament, no port blocks) both cut the L on **+x and
+y**, and output the input plus one copy per style joined, offset +15/+30/+45 in x
(`Column-L` also +15 in y) -- split by x after applying. The nova columns had their flat
sides at -x/+y and were rotated 90 deg clockwise (shells and cores, `*.pre-rotate.stl`).
**Separate-wall column: OpenLock + DragonLock only (no filament). s2w corner column:
OpenLock, DragonLock and Filament** (Devon, 2026-09-29) -- same as dungeon_stone ships.
The columns library is still EXACT: expect zero-volume fins and small open holes; drop the
fins and run `ab core` on each output. Their shells contain internal sheets that split the body; build the core from the pairs
of open shells that close each other and drop the sheets.

### Corners go through `Corner.Right` here

`Corner.Left`/`Corner.Right` (BA library only) remove the base by subtracting
`Filter.Base` (z<=6) rather than cutting, and lock **one end only**: Left at -x, Right at
+x, each adding a 2mm `Corner Block` when `Port Block=True`. aztlan's corner core
narrows at -x (so Left); **nova_trail's narrows at +x, so Right.** Check which end the
corner is on before choosing — compare slab volumes/widths against the plain wall.

The nova corner core also had a 0.2mm lip past the +x mating plane (z 48.1-49.9); it was
trimmed at x=19.05 (0.68mm3), original in `*.corner.core.pre-trim.stl`.

## 7. Open items

- **Partial-port routing isn't in the queue.** `drain.IA` needs `make-ports.py` (its Low
  pair is blocked), but `apply-gaps` routes everything through the node group, which cuts
  all ports. Right now that's only prevented by a warning in the status text. **Fix: encode
  it, e.g. `node_group = "OpenLock;ports"`,** and have `apply-gaps` run the base group then
  `make-ports.py`. Door and window families will hit this often.
- **`--nudge-z -0.02` is confirmed, and it applies to released files too.** Devon passed
  the recut portcullis Q pieces by sight on 2026-09-22 — plain `openforge` as well as the
  side variants. The gross flanges were found on files that **ship in the release tree**,
  which the queue does not model: `option-gaps.tsv` holds only *missing* files. Recutting
  a shipped file means enumerating the release tree directly and mirroring its path into
  `updates/`. dungeon_stone has 60 `*.Q.openforge*.stl` in release and only 16 of them sit

  **`apply-gaps.py` now passes it automatically** (`NUDGE_Z = -0.02`) for any row whose
  first stage group starts with `OpenForge`. `OpenLock` groups are deliberately excluded:
  they make no bottom cut, so a nudge there would just shorten the piece for nothing.
